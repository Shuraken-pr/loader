# AnalyticDashboardDLL

DLL-модуль аналитической панели для основного приложения `pgDelphi`. Модуль отображает события из PostgreSQL, предоставляет агрегированную статистику и обновляет список событий в режиме, близком к реальному времени.

## Текущее состояние

- список событий отображается через`TcxGrid` в unbound-режиме;
- статистика событий отображается через `TcxVirtualTreeList` и `TVTLoadAllDataSource<TEventStatsRecord>`;
- постраничная загрузка событий и LRU-кэш сохранены в `TVirtualDataCache<TEventRecord>`;
- для ограничения одновременных операций с пулом FireDAC используется глобальный `TConnectionSemaphore` и RAII-обёртка `TSemaphoreGuard`;
- проект собирается как Win32 VCL DLL с именем `AnalyticDashboard`.

## Возможности

### Список событий

`TcxGridTableView` (`tvEvents`) работает без обычного набора данных:

1. сначала выполняется запрос `COUNT(*)` для определения общего количества строк;
2. `DataController.RecordCount` получает это количество без создания миллиона объектов;
3. cxGrid запрашивает текст только для отображаемых ячеек;
4. `TVirtualDataCache<TEventRecord>` асинхронно загружает страницы по 1000 записей;
5. пока нужная страница не загружена, отображается плейсхолдер `⌛ ...`;
6. после загрузки страница помещается в кэш, а грид обновляет отображение;
7. при прокрутке дополнительно запрашиваются текущая и следующая страницы.

Кэш хранит не более 50 страниц по умолчанию и вытесняет давно использовавшиеся страницы по LRU. Это ограничивает объём данных в памяти независимо от общего количества записей в таблице.

Колонки списка событий:

- `id`;
- пользователь;
- дата изменения;
- тип события;
- IP-адрес;
- источник;
- статус;
- задержка в миллисекундах.

### Статистика

`vtlEventsStats` использует `TVTLoadAllDataSource<TEventStatsRecord>`. При обновлении статистика полностью загружается в память и отображается в `TcxVirtualTreeList`.

В таблице показываются:

- час;
- источник;
- количество событий;
- средняя задержка;
- скользящий тренд задержки;
- процентный рост относительно предыдущего часа;
- общее количество событий по источнику.

### Real-time обновления

`TRealTimePoller` — отдельный поток, который:

- при запуске запоминает текущий `MAX(id)` таблицы `events`;
- раз в 1000 мс проверяет новый максимальный идентификатор;
- при появлении новых записей загружает только дельту через `public.get_events`;
- передаёт события в UI через `TThread.Queue`;
- добавляет новые записи в начало кэша через `PrependRecord`;
- при ошибке закрывает соединение, ждёт 3000 мс и пытается подключиться снова.

Для poller используется отдельное соединение с `Pooled = False`, поэтому он не забирает слот из пула FireDAC.

### Защита пула соединений

Операции обновления списка событий, обновления статистики и загрузки страниц кэша используют общий семафор:

```text
TConnectionSemaphore.Instance
    └── TSemaphoreGuard
```

Количество слотов семафора устанавливается после чтения настроек пула как `PoolMaxItems - 1`, оставляя резерв для фоновой работы. Таймаут ожидания слота в текущем коде составляет 10000 мс.

## Архитектура

```text
AnalyticDashboard.dll
└── TfrmMain
    ├── grEvents / tvEvents (TcxGridTableView, unbound)
    │   └── TVirtualDataCache<TEventRecord>
    │       ├── постраничная загрузка по 1000 записей
    │       ├── LRU-кэш, до 50 страниц
    │       └── PrependRecord для real-time событий
    ├── vtlEventsStats (TcxVirtualTreeList)
    │   └── TVTLoadAllDataSource<TEventStatsRecord>
    ├── TRealTimePoller
    └── TConnectionSemaphore
```

Основные компоненты:

| Файл | Назначение |
|---|---|
| `Source/AnalyticDashboard.dpr` | Точка входа DLL и экспорт `InitAnalyticDashboard` |
| `Source/main.pas` / `Source/main.dfm` | Форма, гриды, загрузка данных, статистика и FastReport |
| `Source/VirtualDataCache.pas` | Потокобезопасный постраничный кэш событий |
| `Source/RealTimePoller.pas` | Фоновый polling новых событий |
| `Source/uConnectionSemaphore.pas` | Глобальный семафор и `TSemaphoreGuard` |
| `Source/settings.pas` | Вспомогательная модель настроек БД |
| `SQL/Change/001_schema.sql` | Таблицы, вычисляемый `TSVECTOR` и индексы |
| `SQL/Source/002_seed.sql` | Генерация тестовых пользователей и событий |
| `SQL/Source/public.get_events.sql` | Постраничная выборка событий |
| `SQL/Source/public.get_hourly_agg.sql` | Почасовая агрегация и аналитические оконные функции |

Общие зависимости проекта подключаются из каталогов `Common` и `CommonModules`, в частности `cxVirtualTreeListHelper`, настройки подключения, skin-модуль, FireDAC logger и FastReport-интерфейс.

## PostgreSQL

Схема содержит:

- `users` — пользователи;
- `events` — события с `JSONB`-полем `metadata`;
- вычисляемое поле `search_vector` типа `TSVECTOR`;
- индексы по пользователю и времени, типу события, JSONB и полнотекстовому поиску.

`metadata` используется для хранения источника, IP, описания, статуса и задержки. Функция `get_events` извлекает эти значения и возвращает плоский набор колонок для UI.

`get_hourly_agg` использует:

- группировку по часу и источнику;
- среднюю задержку;
- оконное скользящее среднее за три строки;
- `LAG` для расчёта роста;
- оконную сумму общего числа событий по источнику.

## Подготовка базы данных

Из корня `AnalyticDashboardDLL` выполнить скрипты в следующем порядке:

```text
SQL/Change/001_schema.sql
SQL/Source/002_seed.sql
SQL/Source/public.get_events.sql
SQL/Source/public.get_hourly_agg.sql
```

При необходимости для проверки real-time вставки можно выполнить:

```text
SQL/Change/002_test_notify_insert.sql
```

`002_seed.sql` создаёт 1000 пользователей и 500000 тестовых событий за последние 30 дней.

> Скрипты не являются полноценной системой миграций: `001_schema.sql` создаёт объекты без защитных `IF NOT EXISTS`. Повторный запуск на уже подготовленной базе может завершиться ошибкой.

## Сборка и запуск

1. Установить Delphi с VCL и FireDAC.
2. Установить или подключить DevExpress, используемый проектом (`cxGrid`, `cxTreeList`, Ribbon, Layout и skins).
3. Убедиться, что общие исходники из `Common` и `CommonModules` доступны по путям, указанным в `AnalyticDashboard.dpr`.
4. Открыть `Source/AnalyticDashboard.dproj`.
5. Выбрать конфигурацию `Debug` или `Release` и платформу `Win32`.
6. Собрать DLL.
7. Запустить её через основное приложение, поддерживающее интерфейсы `IDLLIntf`, `IDllIntfRun` и `IAnalyticDashboard`.

При первом подключении форма настройки БД позволяет указать параметры PostgreSQL и параметры пула. Используется connection definition `PgPool`. Значения фильтров и настройки подключения сохраняются в `db_settings.xml` рядом с исполняемым файлом основного приложения.

## Фильтры

- диапазон дат применяется к загрузке событий и статистике;
- источник применяется к функции статистики `get_hourly_agg`;
- текущая реализация `RefreshEvents` считывает значение фильтра источника, но не передаёт его в `get_events`, поэтому фильтрация списка событий по источнику пока не реализована;
- real-time poller не присваивает `start_ts` и `end_ts` из фильтров формы в запросе дельты; проверка `MAX(id)` выполняется по всей таблице.

## Обработка ошибок и жизненный цикл

- фоновые операции выполняются через `TTask.Run`;
- обновление визуальных компонентов выполняется через `TThread.Queue` или `TThread.Synchronize`;
- повторный запуск одной и той же операции блокируется флагами и `TCriticalSection`;
- при закрытии формы poller останавливается и дожидается завершения потока;
- соединения, запросы, кэш и источники данных освобождаются в `FormDestroy`;
- ошибки загрузки страниц передаются в UI через `HandleCacheError`.

## Известные ограничения

1. Автоматические тесты в каталоге проекта не обнаружены. Проверка изменений выполняется сборкой DLL и ручным функциональным тестированием.
2. Сортировка, фильтрация и поиск cxGrid не подключены к серверному запросу. Данные списка событий запрашиваются в порядке `id`, заданном `get_events`.
3. Переход по большим диапазонам строк зависит от асинхронной загрузки страниц и может временно показывать `⌛ ...`.
4. `PrependRecord` хранит real-time записи на специальной странице `-1`, однако `GetRecord` вычисляет страницу только как `NodeIndex div PageSize`. Поэтому корректность отображения добавленных в начало записей при одновременной прокрутке и загрузке страниц требует отдельного функционального тестирования.
5. `TRealTimePoller` использует отдельное непулируемое соединение и не обёрнут в `TSemaphoreGuard`; это намеренное текущее поведение, но оно должно учитываться при изменении политики ограничения всех соединений.

## Ручная проверка

После сборки рекомендуется проверить:

1. подключение к PostgreSQL и создание `PgPool`;
2. загрузку списка событий за выбранный диапазон;
3. появление плейсхолдеров и замену их данными при прокрутке;
4. загрузку нескольких страниц и отсутствие резкого роста памяти;
5. обновление статистики и фильтрацию по источнику;
6. появление новой записи в начале списка после INSERT в PostgreSQL;
7. восстановление poller после временного отключения БД;
8. корректное завершение потока при закрытии формы;
9. работу FastReport preview/designer при наличии соответствующей DLL.
